1. 진행 중인 사업과 자료 준비

신한은행 컨테이너 모니터링

RFP가 8월, 늦어도 9월 초에 공고됩니다. 10월 안에 구축 예정이고 엑셈과 와탭, 엔키아가 경쟁합니다. 기술점수와 가격점수로 평가하되 비율은 미정입니다. 신한은행 내부에서 쿠버네티스 환경이 계속 늘고 있어 뒤에 붙는 사업이 많다고 보며, 우선 수주가 중요하다는 판단입니다. 1차 의견은 세 제품 간 변별력 부족이었습니다.

재료 위치엑셈원 8월 릴리즈(8/20)에 쿠버네티스 개선 포함. 26.12 예정 과업 클릭업 태스크 3건이 실제 고객 요구입니다. DSP-42846(KB라이프 Workload Overview), DSP-44090(컨테이너 상세 리소스 관계도), DSP-44088(Network Service 프록시 유형별 지표). 통합개발본부 항목에 KB라이프 K8s 고도화로 virtual service 표현과 리포트 개선이 있습니다.
물어볼 사람이슬기, 이택기, 이경준 (K8s 기술 기획). 딜 상황은 강대일 상무
주제변별력 부족이 문제였으니 기능 목록 나열은 효과가 없습니다. "쿠버네티스만 보는 도구와 APM, DB까지 한 화면에서 보는 도구의 차이"가 축입니다. 컨테이너 지표는 어디나 보여주지만, 컨테이너에서 시작해 트랜잭션과 DB 쿼리까지 한 번에 내려가는 건 엑셈원 구성이라야 됩니다. 클릭업 3건이 다 "관계"를 보는 요구(리소스 관계도, virtual service, 프록시 유형별)라 이 축과 맞습니다.
형태제안서에 붙일 2장. 1장은 컨테이너에서 DB까지 내려가는 화면 순서, 1장은 평가표 대응용 기능 대조
언제까지공고가 8월 중 열릴 수 있어 8월 셋째 주까지
삼성생명 인터맥스 E2E

제니퍼를 걷고 들어가는 건이고 인터맥스와 와탭이 경쟁합니다. 1년 사이트 라이선스 1억 9,000만 원 규모입니다. 고객에게 E2E 모니터링이 필수라는 점은 인식시킨 상태이고, PoC에서 인터맥스로 E2E가 이어지는 것을 보여주면 수주에 도움이 된다고 봅니다. 삼성SDS FEP AnyFrame 구간만 진행 예상이며, SAP Java 부문은 담당자가 시스템 변경을 부담스러워합니다. 회의 중 PoC 잠정 중단 연락이 왔고 사유는 확인 중입니다.

재료 위치한국예탁결제원 고객평이 그대로 근거입니다. "직책자분들 그리고 업무담당자들 모두 인터맥스 화면만 봅니다. 거래가 모두 연결되어 있어 좋아합니다." 광주은행 E2E 사업도 계약 전 거래 추적 대상 구간 확인부터 시작했습니다.
물어볼 사람E2E기술그룹 (구 APM기술그룹)
주제"거래가 끊기지 않고 이어져 보이면 무엇이 달라지는가"입니다. 예탁결제원 고객평이 정확히 그 말이라 인용이 근거가 됩니다. SAP나 ABAP처럼 손대기 부담스러운 구간을 어떻게 다루는지도 같이 넣으면 삼성생명 상황에 맞습니다.
형태1장 자료 + 제품 페이지 E2E 항목 갱신
언제까지PoC 재개 시점. 중단 사유 확인 후 일정 잡기

2. 이슈사항 두 건

고객이 자체 개발을 시작했습니다 (현대해상)

IT자회사 현대HDS가 AI를 활용해 자체 DB 성능 모니터링 툴을 개발하고 계속 고도화하는 중입니다. CIO가 기간계 DB 서버에 적용하라고 지시했고, 이광목 과장이 안정성과 운영 리스크를 설명해 현재는 적용을 방어한 상태입니다. 영업본부 자료에 "향후 AI 기술을 활용해 모니터링 솔루션을 자체 개발하려는 고객사가 점차 증가할 것으로 예상됨"이라고 적혀 있습니다.

재료 위치스프레드시트 기술개발 시트의 맥스게이지 고객 대응 요약이 통째로 재료입니다. 원인 규명에 공수가 크게 들어간 사례가 실명으로 정리돼 있습니다. 폭스바겐 수집 누락은 한 달치 로그 분석 끝에 대상 DB나 제품 로직이 아니라 수집 서버 프로세스가 메모리 한계에 도달해 주기적으로 멈춘 것이 원인이었습니다. 케이카캐피탈 RTS 반복 경고는 수집에 영향 없는 가드 로그로 확인해 제거했습니다. 대법원 AIX Tibero 7은 패키지에 표준 OpenSSL 심볼이 없어 데몬이 기동되지 않았고, 고객사 OpenSSL을 주입해 넘긴 뒤 Tibero 측 수정 바이너리로 재빌드했습니다. 하나은행과 KB증권은 같은 시기에 동일 증상을 보고했습니다.
물어볼 사람이광목 과장. CIO 지시를 어떤 말로 막았는지가 그대로 우리 논리입니다. 사례 인용 가능 범위는 제품기술연구그룹
주제우리 자료는 지금 대부분 경쟁 제품과 비교하는 각도인데 자체 개발과 비교하는 각도가 없습니다. "직접 만들면 처음엔 되는데 어디서 막히는가"로 씁니다. 근거는 세 가지입니다. 하나, 장애 원인이 제품 밖에 있을 때(수집 서버 메모리, OS 라이브러리) 이를 규명하는 데 드는 공수. 둘, 우리 통제 밖 변수(DB 벤더 패키지 정합)가 기동 자체를 막는 상황. 셋, 이기종 DB 지원 범위로 MaxBot이 Tibero와 DB2, Altibase를 더하고 9월에 SQL Server와 Postgres까지 갑니다. 자체 개발은 보통 한두 종에서 멈춥니다.
형태블로그 1편 + 영업용 1장. 고객사명은 전부 익명 처리
주의현대해상 건 자체는 언급 금지입니다. 지금 방어 중인 상황이라 외부에 나가면 고객사 내부 문제가 됩니다
조달청 미검색으로 건을 놓쳤습니다 (질병관리청)

윗선 영업으로 MaxGauge 도입이 진행되던 상황에서 실무진이 여러 제품을 검토했고, 7월 22일 구매 진행 도중 엑셈 제품이 조달청에서 검색되지 않아 셀파 구매로 이어졌습니다. 우리은행 PaaS 모니터링 PoC는 사업 공고일이 부정당 제재 기간 내에 있어 참여가 제한됐습니다.

우리 쪽 의미콘텐츠 과업은 아닙니다. eXemble 조달 등록 소식을 언제 어떻게 알릴지 정할 때 근거로 씁니다. 등록이 서류 절차가 아니라 매출이 빠지는 문제라는 실물 사례입니다. 5번 항목의 발표 시점 판단과 같이 보십시오.

3. 제품 명칭과 설명 방식

회의에서 AXIS와 ExTuner, ExpertSQL, AIM, Ask MaxGauge가 한꺼번에 나와 정리가 안 된 것처럼 보였지만, DB기술본부 과업보고를 보면 내부 계층은 이미 잡혀 있고 담당자도 실명으로 지정돼 있습니다.

차세대 MaxGauge
 ├ 제품 기능: 멀티테넌트와 RAC / EXADATA / ExpertSQL
 └ AIM (AI In MaxGauge)  = AI 기능 묶음 이름
    ├ RCA                (장기협 그룹장)
    ├ X-TUNER 연계        (유정오 팀장, 이동기 과장)
    ├ Ask MaxGauge        (김형웅 팀장)
    ├ 통계기반 이상탐지    (김민수 과장, 남병민 과장)
    ├ MaxGauge In Chrome  (이충건 과장, 김재덕 과장)
    └ AXIS 엔진 제품화     (박준연 본부장, 김병오 과장)

exemONE DPM  = 별도 축. 본부에서 가장 많은 인원이 붙어 있음
재료 위치AXIS 자료가 두 종 있습니다. 임원회의 발표용은 8장으로 정리돼 문구와 5단계, 수치가 다 들어 있습니다. 본부원 공유용은 1만 7천 자 분량으로 개발 과정과 한계까지 담겨 있습니다. 둘 다 회의 첨부 zip 안에 있습니다.
물어볼 사람박준연 이사, 김병오 과장 (AXIS 제품화 담당)
우리가 할 일이름을 새로 짓는 일이 아닙니다. AIM이 묶음 이름이고 AXIS가 그 안의 엔진이라는 관계를 고객이 알아듣게 쓰는 일입니다. ExTuner는 별도 제품이라 섞이지 않게 선을 그어야 합니다.

임원 발표용에 이미 쓸 만한 문구가 있습니다. 새로 짓는 대신 다듬는 쪽이 빠릅니다.

  • "SQL 튜닝 판단을 반복 가능한 시스템으로"
  • "느린 SQL을 보고 최선의 조치만 남기는 엔진"
  • "개인의 감각에서 증거로 반복되는 조직의 튜닝 절차로"
  • "좋아 보이는 SQL이 아니라 DB에서 이긴 후보만 보존"

다섯 단계도 정해져 있습니다. 입력 이해, 병목 우선순위, 대안 경쟁, DB 실측, 재진단입니다. 제품 페이지 구성을 이 순서로 잡으면 됩니다.

본부원 공유용에는 실패 과정이 남아 있습니다. LLM과 SFT만으로는 제품 경로가 닫히지 않았고, 룰 엔진으로 바꾼 뒤에도 모듈마다 plan text를 따로 읽어 같은 사실을 다르게 해석하는 문제가 있었다고 적혀 있습니다. 기술 블로그로 풀면 깊이가 나오는 소재지만 대외 공개 여부는 박준연 이사 확인이 먼저입니다. 개발 실패 과정은 경쟁사에도 힌트가 됩니다.

(고평석 대표) "엑셈 DB 엔지니어들이 축적한 암묵지가 들어가 있음. 이를 AI화, 솔루션화한 기술로 전달할 수 있도록 제품 명칭과 설명 방식도 함께 고민할 필요"

4. exemONE SingleStore, 지금 쓸 수 있는 소재

회의 첨부에 exemONE SingleStore 제품 문서가 들어 있었습니다. 회의록 본문에는 언급이 없었지만 콘텐츠로는 이번 달 재료 중 가장 완성도가 높습니다. 7월 SingleStore AI NOW 행사에 부스로 참가한 이력도 있어 이어가기 좋습니다.

문서가 잡아둔 문제 정의 네 가지가 그대로 블로그 목차가 됩니다.

  1. 노드는 정상인데 서비스는 지연됩니다. Leaf 8대 모두 CPU가 정상인데 원인은 파티션 편중에 있습니다
  2. 어느 구간에서 느려졌는지 모릅니다. 병합이 느린지 실행이 느린지 SQL 하나 안에서 구분되지 않습니다
  3. 복제가 따라오고 있는지 모릅니다. 복제 지연은 장애가 나기 전까지 어떤 상태값에도 드러나지 않습니다
  4. 설정이 서로 같은지 모릅니다. 같은 역할인데 설정이 다르면 노드를 하나씩 조회해야 압니다

문서의 결론이 "네 가지 모두 개별 Node 지표가 아니라 Cluster 구조에서 발생하는 문제"입니다. 이 한 문장이 우리 메시지 축입니다. 진단 체계는 CORE 8로 정리돼 있고 영역별 수집 주기까지 명시돼 있습니다.

CORE영역수집 주기
1Cluster 구성과 Node 상태1일 / 5초
2리소스 사용량과 Skew5초
3파티션 분포와 복제 동기화10분
4테이블 설계와 압축1분 / 10분
5분산 쿼리 성능5초 / 10분
6Pipeline 적재1분
7USD와 Object Storage1분 / 10분
8파라미터, 이벤트, 라이선스1일 / 1분

경쟁사 상황을 확인했습니다. 와탭이 이미 SingleStore를 지원 목록에 넣고 문서까지 갖춰뒀습니다. 검색으로 우리 글이 나오려면 같은 얘기를 반복해서는 안 됩니다.

  • 와탭 SingleStore 문서: docs.whatap.io/singlestore/monitoring-intro (인스턴스, 멀티 인스턴스, 스토리지 엔진, 파티션, 파이프라인, DB 크기, Top SQL, 세션 이력, Lock Tree)
  • 지원 DB 목록에 SingleStore 포함: whatap.io/ko/products/database/ (15종)
  • 과금은 Leaf Node 기준: whatap.io/en/pricing
  • 와탭 강조점은 설치 편의입니다. 애그리게이터에만 에이전트를 설치하면 리프 노드를 자동으로 찾습니다

우리 문서에는 있고 와탭 문서에서는 안 보이는 항목이 차별 지점입니다. 복제 동기화를 Log Position 차이로 수치화하는 것, USD와 Object Storage를 LSN으로 동기화 지연을 정량 추적하고 Blob Cache 적중률까지 보는 것, 전 노드 파라미터 중 차이 항목만 Diff로 뽑는 것, 라이선스 Capacity를 노드별과 클러스터 합계로 보는 것, 테이블의 Shard와 Primary, Sort Key 지정 여부를 테이블 단위로 확인하는 것입니다.

주제"Leaf 노드 CPU가 다 정상인데 왜 느린가"로 시작하는 글입니다. 문서의 난제 1번을 제목으로 쓰면 검색 의도와 맞고, 와탭 문서가 다루지 않는 파티션 편중과 복제 지연 수치화로 이어갑니다. 2편으로 나눠 1편은 문제 네 가지, 2편은 CORE 8 중 복제와 설정 편차를 깊게 파는 구성이 좋습니다.
형태기술 블로그 2편 + 제품 페이지에 SingleStore 항목 신설. 7월 SingleStore AI NOW 부스 참가 이력과 묶으면 행사 후속 콘텐츠가 됩니다
확인 필요제품 문서가 대외 배포용인지 내부용인지, 화면 캡처를 콘텐츠에 쓸 수 있는지
